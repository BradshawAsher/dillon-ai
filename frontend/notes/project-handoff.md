# Financial Due Diligence Agent — Project Handoff

## 1. What this product is

This app is an internal M&A / financial due diligence workspace intended to help during the post-LOI diligence window.

The long-term goal is **not** just single-document extraction.
The intended product direction is:

- users create or work inside a **project / deal dossier**
- users upload **multiple documents** related to one acquisition target
- each document is processed asynchronously
- the system extracts structured financial / diligence insights from each file
- the system then **reconciles all project documents together**
- the final deliverable is **one project-level judgment** about the acquisition, including:
  - risk assessment
  - contradictions across documents
  - missing diligence materials
  - negotiation leverage / cost-down opportunities
  - valuation range / supportability
  - investment thesis / recommendation

This project started as a single-document async intake tool and has now been refactored so the UI and data model are moving toward a **project-centric, multi-document diligence agent**.

---

## 2. Business context / intended use case

Primary use case:
- 30 days post-LOI
- financial due diligence
- finding inconsistencies, unsupported seller claims, bad add-backs, margin compression, missing profitability support, customer concentration issues, and other items that help with negotiation leverage

The app is intended to function more like a **diligence partner** than a file parser.

That means the system should eventually answer questions like:
- Do the uploaded documents agree with each other?
- What key diligence materials are still missing?
- Which management claims are unsupported?
- What should be escalated for human review?
- What lowers confidence in earnings or valuation?
- What can be used to renegotiate price or terms?

## 3. Architecture philosophy

### Current architecture
The project uses an asynchronous “factory” model:

1. Frontend uploads a file and metadata.
2. A lightweight n8n webhook accepts the request quickly.
3. n8n stores metadata in a table / row and starts background processing.
4. A sub-workflow performs AI parsing / extraction.
5. The frontend polls for status and row updates.
6. When the row changes, the frontend displays the updated outputs.

### Why polling is used
Polling was implemented because the AI/document workflow is too long-running for a single blocking request.

Instead of waiting for a long response, the flow is:
- submit fast
- get acknowledgment
- keep checking every 5 seconds
- render the updated row when status / outputs change

This is already working.

## 6. Polling implementation details

Polling is implemented in:
- `/frontend/pages/DueDiligenceDashboard.tsx`

Mechanism:
- the app fetches submission history via `useGetSubmissionHistory()`
- if any row is in an active state, it starts a `setInterval`
- every 5 seconds it calls:
  - `triggerSubmissionHistory({ environment }, { skipCache: true })`
- polling stops automatically when no active rows remain

Active statuses are defined in:
- `/frontend/utils/submissionHistory.ts`

Current active set:
- accepted
- queued
- processing
- received
- running
- submitted

The latest submit panel uses the latest submission `requestID` from `submitDealPacket` response and finds the matching row in polled history.

This function is critical and currently supports many fields from n8n.

- used by the findings table in the UI
- still useful, but not yet aligned to the project-synthesis direction

### `/backend/diligence/submissionPayload.ts`
Purpose:
- webhook path utilities and submit response normalization

## 13. What is still missing / not done yet

### A. True multi-document processing
The app still submits only **one file at a time**.

This is okay for now, but the system still needs either:
- repeated uploads into one project, or
- future batch-upload support

### B. Project-level synthesis workflow in n8n
This does **not** exist yet in the app code.

Needed:
- a workflow that fetches all document rows for one `projectId`
- reconciles structured outputs across them
- writes final project-level outputs somewhere accessible

### C. Project-level result rendering
The UI has project grouping, but not yet:
- project-level final memo
- cross-document contradictions
- missing-doc workflow state from backend
- final acquisition recommendation generated from all docs

### D. Dedicated project detail page / route
Currently everything is on one dashboard page.
A future builder may want to add:
- `/projects/:projectId`
- project detail tabbed interface
- documents / conflicts / recommendations / final memo views

## 14. What n8n needs to do next

These are the most important backend / workflow tasks still needed.

### Minimum immediate n8n changes
Add / preserve these fields on rows:
- `projectId`
- `projectStage`
- `documentType`

And ensure they are:
- accepted on intake
- stored on insert
- preserved on update
- returned on history polling

### Strong next-step changes
Create a **project synthesis** layer.

Recommended logic:

#### Per-document workflow
For each document:
- classify doc
- extract structured facts
- identify flags
- store row outputs

#### Project-level workflow
When enough project docs exist for one `projectId`:
- fetch all rows for that project
- compare facts across documents
- detect contradictions
- identify missing diligence materials
- consolidate negotiation levers
- write project-level judgment

### Recommended project-level fields / storage
Use either a second n8n table or project-level records with fields like:
- `projectId`
- `projectStatus`
- `documentsReceivedCount`
- `documentsCompletedCount`
- `missingDocumentsJson`
- `crossDocumentConflictsJson`
- `openQuestionsJson`
- `negotiationLeversJson`
- `finalRiskLevel`
- `finalTrafficLight`
- `finalRecommendation`
- `finalJudgmentJson`
- `projectProcessedAt`

## 15. Known limitations / caveats

1. The project portfolio is currently inferred from document history, not from a dedicated project table.
2. Coverage checklist is heuristic and based on `documentType` labels, not on robust backend project state.
3. The UI is ready for project data, but n8n may still be returning blank `projectId`, `projectStage`, and `documentType` if not yet added.
4. The legacy `getDiligenceData` panel is still document-level / Retool DB based and not yet converted into project synthesis output.
5. The app currently supports only single-file submit per action.
